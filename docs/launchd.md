# launchd

> **Maintainer note:** update this doc when (a) a service is added,
> removed, or renamed in `launchd.py`, (b) a plist field changes
> shape (env vars, interval, KeepAlive vs StartInterval), (c) the
> watchdog thresholds (`MAX_TUNNELD_UPTIME_SECONDS`,
> `STALE_EMPTY_THRESHOLD_SECONDS`) in `tunneld_keepalive.py`
> change, or (d) the install/uninstall sudo dance changes.

## What this is

Torch runs three persistent services under macOS launchd. This
doc covers each plist, the install/uninstall flow, and the
watchdog daemon's logic.

## The three services

```
+-------------------------------+--------+-----+----------------------+
| Label                         | Where  | UID | What                 |
+-------------------------------+--------+-----+----------------------+
| com.torch.tunneld             | System | 0   | pymd3 remote tunneld |
|                               |        |     | --wifi               |
+-------------------------------+--------+-----+----------------------+
| com.torch.tunneld-keepalive   | System | 0   | python -m            |
|                               |        |     | torchapp.            |
|                               |        |     | tunneld_keepalive    |
|                               |        |     | (every 30 min)       |
+-------------------------------+--------+-----+----------------------+
| com.torch.app                 | User   | $UID| /Applications/       |
|                               |        |     | Torch.app/Contents/  |
|                               |        |     | MacOS/Torch          |
+-------------------------------+--------+-----+----------------------+
```

Plist files land at:

```
/Library/LaunchDaemons/com.torch.tunneld.plist
/Library/LaunchDaemons/com.torch.tunneld-keepalive.plist
~/Library/LaunchAgents/com.torch.app.plist
```

## com.torch.tunneld (main tunnel daemon)

Generated by `launchd.tunneld_plist()`. Key fields:

```python
{
  "Label": "com.torch.tunneld",
  "ProgramArguments": ["/opt/homebrew/bin/pymobiledevice3", "remote", "tunneld", "--wifi"],
  "EnvironmentVariables": {
    "HOME": "/Users/<installing-user>",   # bake user's HOME in
    "PATH": "<inherited from install env>"
  },
  "RunAtLoad": True,
  "KeepAlive": True,                       # respawn on crash
  "StandardOutPath": "/var/log/torch-tunneld.out",
  "StandardErrorPath": "/var/log/torch-tunneld.err",
  "ThrottleInterval": 30,
}
```

Two non-obvious fields:

- `HOME` is baked in. Without this, root's HOME defaults to
  `/var/root` and tunneld can't see the user's
  `~/.pymobiledevice3/` pair records. It would still pick up
  USB devices via usbmuxd (kernel-mediated, HOME-independent)
  but RemotePairing on Wi-Fi would fail. We set HOME to the
  installing user's home so root's tunneld reads from the same
  directory the manual-sudo dev workflow uses.
- `KeepAlive: True` so the daemon respawns on crash.
  `ThrottleInterval: 30` rate-limits respawn loops (so a
  consistently-crashing tunneld can't peg CPU).

The pymobiledevice3 CLI path is resolved by
`_pymobiledevice3_bin()` which prefers the binary next to the
currently-running Python interpreter (i.e. inside the venv that
installed Torch), falling back to `which`. This guarantees the
plist points at a pymobiledevice3 that has the correct package
installed.

## com.torch.tunneld-keepalive (watchdog)

Generated by `launchd.tunneld_keepalive_plist()`. Runs the
watchdog script every 30 minutes.

```python
{
  "Label": "com.torch.tunneld-keepalive",
  "ProgramArguments": ["<venv python>", "-m", "torchapp.tunneld_keepalive"],
  "EnvironmentVariables": {
    "HOME": "/Users/<installing-user>",
    "PATH": "<inherited from install env>",
    "PYTHONPATH": "/Volumes/T7/Projects/ATVLoader/src",
  },
  "RunAtLoad": True,                       # fire once immediately
  "StartInterval": 1800,                   # 30 min cadence
  "StandardOutPath": "/var/log/torch-tunneld-keepalive.log",
  "StandardErrorPath": "/var/log/torch-tunneld-keepalive.log",
  "ThrottleInterval": 60,                  # rate-limit respawn loop
}
```

The watchdog deliberately lives outside the Torch.app bundle:

- It needs root to issue `launchctl kickstart -k system/...`. The
  user-mode Torch.app can't sudo from inside the Cocoa runloop.
- Putting the watchdog in its own LaunchDaemon keeps the
  privilege surface tiny -- the only thing this daemon ever does
  is restart its sibling tunneld daemon.
- It's a non-critical service. Worst case if it fails: user
  manually kicks tunneld when they notice (which they did
  exactly once before the watchdog existed).

`PYTHONPATH` points at the repo's `src/` directory so the venv
python can `import torchapp.tunneld_keepalive`. This couples the
watchdog to the source tree -- moving or deleting the repo
breaks the watchdog, but that's no worse than the main tunneld
daemon which also depends on the venv staying put.

Watchdog logic (`torchapp/tunneld_keepalive.py:main`):

```
1. Find tunneld process via pgrep -f 'pymobiledevice3 remote tunneld'.
   If absent: log, exit 0. (com.torch.tunneld has KeepAlive=True,
   will respawn on its own.)

2. Read tunneld uptime via ps -o etime= (BSD ps; we parse the
   formatted [DD-]HH:MM:SS shape ourselves since macOS doesn't
   support etimes).

3. Read tunneld inventory size via GET http://127.0.0.1:49151/.

4. Count pair records on disk in ~/.pymobiledevice3/remote_*.plist
   (the "we expect at least one device" baseline).

5. Decide:
   - if uptime > 7 days: RESTART (mDNS state rot preemption)
   - elif uptime > 6h AND inventory == 0 AND pair_records > 0:
     RESTART (empty-inventory check; catches the failure mode
     earlier when it presents inside a normal-looking week)
   - else: no-op

6. If RESTART: launchctl kickstart -k system/com.torch.tunneld.

Every check + restart logs to /var/log/torch-tunneld-keepalive.log
with timestamp + uptime + inventory + pair_records + reason.
```

The 7-day and 6-hour thresholds came from the 2026-06-20 incident
where tunneld hit 44 days uptime with empty inventory. 7 days is
the largest "safe" uptime we've actually run with no issues; 6
hours is short enough to catch problems within the same calendar
day without being so aggressive that normal "all devices off
overnight" triggers a restart.

## com.torch.app (menubar LaunchAgent)

Generated by `launchd.app_plist()`. Runs the py2app-built bundle
launcher directly, not `python3 -m torchapp` -- this is what
gives the process a proper CFBundleIdentifier so notifications
attribute to "Torch" instead of "Python."

```python
{
  "Label": "com.torch.app",
  "ProgramArguments": ["/Applications/Torch.app/Contents/MacOS/Torch"],
  "EnvironmentVariables": {
    "HOME": "/Users/<installing-user>",
    "PATH": "<inherited from install env>",
  },
  "RunAtLoad": True,
  "KeepAlive": True,
  # ... StandardOutPath, StandardErrorPath, ProcessType: Interactive
}
```

The launcher path is resolved by `_torch_app_executable()` which
prefers `/Applications/Torch.app` (production install), falls
back to `<repo>/dist/Torch.app` (dev alias build). See
[packaging.md](packaging.md) for the difference.

`PYTHONPATH` is deliberately NOT set here. py2app's `__boot__.py`
sets up its own `sys.path`; leaking the system PYTHONPATH would
cause the bundle to pick up system site-packages on top of its
own, risking rumps / pyobjc version skew.

## Install / uninstall flow

```bash
# Install everything (typical first-run)
python3 src/install.py

# Install only the user LaunchAgent (no sudo prompt; for dev iteration)
python3 src/install.py --agent

# Install only the system LaunchDaemons (sudo prompt once)
python3 src/install.py --daemon

# Skip the bundle rebuild (use existing /Applications/Torch.app or dist/)
python3 src/install.py --skip-build

# Alias-build mode for dev iteration (~3s rebuild, symlinks Resources)
python3 src/install.py --agent --alias
```

The system daemons (tunneld + keepalive) are installed via a
single `osascript do shell script ... with administrator
privileges` call so macOS prompts for the admin password through
its own native dialog. We never touch the password ourselves.

Sequence per daemon install (`install_launch_daemon`,
`install_tunneld_keepalive`):

1. Write plist to `~/Library/Application Support/Torch/<label>.plist.staging`
   (user-writable).
2. Compose a single shell script that:
   - `mv` staging plist to `/Library/LaunchDaemons/<label>.plist`
   - `chown root:wheel`
   - `chmod 644`
   - `touch` and `chmod 644` the StandardOutPath / StandardErrorPath
     log files (so launchd can open them without fighting SIP)
   - `launchctl bootout system <path>` (best-effort, suppressed
     with `|| true` since "not loaded" is non-fatal)
   - `launchctl bootstrap system <path>`
3. Pass the chained script to `_run_as_admin` which wraps it in
   `osascript -e 'do shell script "..." with administrator privileges'`.

The user LaunchAgent install (`install_launch_agent`) doesn't
need sudo. It writes directly to `~/Library/LaunchAgents/`,
`launchctl bootout`, then `launchctl bootstrap gui/$UID`.

Uninstall follows the inverse pattern -- bootout then `rm` the
plist. Uninstalling the main tunneld daemon also uninstalls the
keepalive (in `uninstall.py`); we don't want the watchdog left
behind running against a tunneld that no longer exists.

## Status helpers

```python
launchd.is_service_loaded(label, *, domain) -> bool
launchd.is_tunneld_daemon_loaded() -> bool
launchd.is_app_agent_loaded() -> bool
```

These run `launchctl print <domain>/<label>` and check
exit code. Used at startup to detect "Torch.app is running but
tunneld isn't" states and surface them in the menubar.

## Log file locations

```
/var/log/torch-tunneld.out                  # tunneld stdout
/var/log/torch-tunneld.err                  # tunneld stderr (most useful)
/var/log/torch-tunneld-keepalive.log        # watchdog every-tick log
~/Library/Application Support/Torch/logs/torch.log   # Torch.app log
~/Library/Application Support/Torch/logs/launchd.err # Torch.app launchd stderr
~/Library/Application Support/Torch/logs/launchd.out # Torch.app launchd stdout
```

The Torch.app log file occasionally gets unlinked by macOS
cleanup tooling or third-party "cleaner" apps. When that happens
the FileHandler inside the running Torch process holds an
orphaned inode -- new entries still go to the orphan but `ls`
shows the file as missing. Kickstart Torch
(`launchctl kickstart -k gui/$(id -u)/com.torch.app`) to release
the orphan and create a fresh log file. See "log file
disappearing" failure mode in [refresh.md](refresh.md).

## Key files

- `src/torchapp/launchd.py` -- plist generators + install/uninstall
- `src/torchapp/tunneld_keepalive.py` -- watchdog entry point
- `src/install.py` -- install flow that calls into launchd.py
- `src/uninstall.py` -- inverse

## Common failure modes

| Symptom | Likely cause | Fix |
|---|---|---|
| tunneld respawn loop (rapid restarts in launchd.err) | KeepAlive triggering on a crash bug; ThrottleInterval=30 rate-limits | check tunneld.err for the recurring error; usually pymd3 version skew |
| Watchdog log file at `/var/log/torch-tunneld-keepalive.log` is empty | StandardOutPath / StandardErrorPath not touched at install | re-run `python3 src/install.py --daemon` |
| User runs `--daemon` install but no sudo prompt | osascript cached admin auth for this session | benign -- the install ran with already-granted privileges |
| Torch.app process keeps quitting | rumps API misuse from worker thread (see [ui.md](ui.md)) | check launchd.err -- silent Cocoa abort leaves no traceback in torch.log |
